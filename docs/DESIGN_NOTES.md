## Прямой авторский замысел

### U1. Публичная основа для обсуждения реформы

> Про однозначность ещё - я просто хочу в будущем иметь наглядную систему, которая бы публике была продемонстрирована как основа для начала реформирования УК, его упрощения и сокращения числа норм и гуманизации наказаний.

Следствие для плана: ближайший содержательный результат должен показывать уголовно-правовой эксперимент и объяснять изменения правил. Переносимость на другие домены остаётся отдельной инженерной целью.

### U2. Прозрачное обязательное смягчение

> На счет гуманности. Я думаю прозрачность и однозначность вердикта должна побудить к более богатой и опять же прозрачно логике: условно если есть наказание в 10 лет лишения свободы, то если истинно условие А - такое наказание сокращается на треть. А не потому, что судья сжалился.

Инженерная интерпретация: после мотивированного установления условия преобразование обязательно. Полнота применения норм и взаимодействия между ними становятся самостоятельными проверяемыми свойствами. Ожидаемое влияние прозрачности на разработку более гуманных норм остаётся исследовательской гипотезой.

### U3. Архитектура в Hypercode

Автор попросил описать архитектуру сервиса в нотации Hypercode и затем подтвердил: «Hypercode работает как я и задумывал». Следующий вопрос касался вида ссылки из `.hcs` на спецификацию SpecGraph. Этот вопрос не фиксирует готовый integration API.

### U4. Действия, отношения и последствия — 2026-10-24

В текущей переписке автор предложил ядро Entity / Action / Role / Relation,
Ответственные отношения и условия на состояния сущностей. Уточнения автора:

> Последствие это буквально diff от двух State

> Ещё один из принципов это непременно опора на Действие человека (или бездействие)

Автор отдельно потребовал сначала аппарат доказательства внутри изолированных
слоёв, например Relations, и поручил закрепить обсуждение, выполнить первый шаг,
а затем применить его к парковке. [Документ оснований](RELATIONAL_FOUNDATIONS.md)
отделяет эти Intent от инженерного выбора typed ground Horn rules и Lean.
[Issue #203](https://github.com/SoundBlaster/NormLab/issues/203) ведёт первый срез;
States/diff, action bridge и предметная интеграция остаются последующими этапами.

Продолжение 2026-10-25: R2a — конечные состояния отношений и точный diff
([#221](https://github.com/SoundBlaster/NormLab/issues/221)); R2b — проверяемое
дерево вывода и сохранение его опоры при удалении
([#223](https://github.com/SoundBlaster/NormLab/issues/223)). Связь с человеческим
действием/бездействием и перенос на парковочный пилот остаются следующими слоями.

Уточнение автора 2026-10-25: актор может быть абстрактной сущностью, например
сообществом, а не только человеком или группой. В R3 actor имеет общий тип Entity;
человеческий вклад (`humanAnchor`) связывается с ним отдельным основанием
атрибуции. [Контракт R3](ACTION_ATTRIBUTION.md),
[Issue #225](https://github.com/SoundBlaster/NormLab/issues/225).

## Владение семантикой

```text
Архитектура .hc/.hcs
    → Hypercode resolved IR
    → NormLab architecture adapter
    → контракты и ограничения компонентов

Нормативное authoring-представление .hc/.hcs
    → Hypercode resolved IR
    → NormLab legal-data adapter
    → typed Legal IR + semantic profile + locks
    → immutable NormBundle
    → interpreter → candidate / ledger / certificate
    → independent verifier → receipt
```

Это целевые пути. В M0 нормативные fixtures внесены в типизированный реестр вручную; reference Hypercode pipeline пока не подключён.

Hypercode отвечает за композицию, иерархию и разрешение свойств. Смысл `MandatoryRule`, `NormPackage`, ссылок между доменными объектами и юридического приоритета задают adapters NormLab. Specificity и порядок строк `.hcs` не являются порядком применения правовых норм.

Resolved IR архитектуры и Legal IR — разные артефакты. Проверка primitive property contract не доказывает runtime enforcement или корректность нормативной модели. `hypercode diff` в этой архитектуре используется для сравнения resolved representation; equivalence последствий относится к ComparisonService.

Выбор между TypeScript producer с Lean checker и compiled Lean interpreter остаётся Open. Он не должен менять требования к независимому отношению допустимости, полноте правил и bindings.

## Предложение интеграции со SpecGraph

Ниже сохранено **предлагаемое соглашение из чата**. Оно не описывает существующий API, зарегистрированные спецификации или работающий resolver. Идентификаторы условные.

Для одной связи:

```hcs
'#ai':
  spec_ref: "specgraph://normlab/specs/SG-0042?revision=7#no-fact-writes"
  spec_relation: "constrained-by"
```

Для нескольких обязательств предлагаются отдельные дочерние узлы `SpecBinding`. Их родитель — субъект связи; поля `spec_ref` и `relation` задают цель и смысл; необязательное `subject_property` уточняет свойство компонента.

Требования к будущему adapter:

1. Использовать стабильные ID спецификации и пункта, точную revision и digest содержимого.
2. Проверять разрешение ссылки, отношение и доступ к источнику; фиксировать зависимости в lock или snapshot.
3. Учитывать каскад: обычное строковое `spec_ref` заменяется более специфичным значением, накопление обязательств само собой не возникает.
4. Разделять декларацию `constrained-by` и evidence конкретной проверки, поддерживающее или опровергающее соответствие.
5. Не скачивать и не исполнять содержимое ссылки автоматически в core Hypercode; разрешать её отдельным контролируемым шагом adapter.
6. Делать недоступную обязательную ссылку или несовпавший digest явной ошибкой, без скрытого перехода к `latest`.

SpecGraph остаётся опциональным потребителем/источником traceability. Для вычисления последствий и проверки квитанции чистому ядру NormLab не требуется сетевой доступ к SpecGraph.

## Открытые решения

Первый набор правил A/B/C, domain D16 и ожидаемые различия зафиксированы в [reform fixture v0.1.0](../fixtures/reform-v1/README.md). [Contracts v2 и semantic profile](CONTRACTS.md) реализованы отдельным ядром. Для этого среза выбран TypeScript producer с отдельным [Lean decision checker](REFORM_VERIFICATION.md); decision obligations NL-106 подтверждены. [NL-405](COMPARISON_VERIFICATION.md) реализует comparison/property proofs, receipts и локальный replay; [NL-406](EXPLANATIONS.md) — deterministic explanations; [NL-108](METRICS.md) — отдельные метрики с зафиксированными единицами. [NL-502](LABORATORY_UI.md) предоставляет локальный React UI и HTTP API с immutable snapshots/analyses, историей findings, A/B/C, fresh replay и export. Этот срез работает с reviewed synthetic fixtures; внешний package import остаётся отдельной задачей.

| Решение                                                   | Когда требуется                                                        |
| --------------------------------------------------------- | ---------------------------------------------------------------------- |
| Процедурный смысл `not-established` для иных профилей     | При расширении за пределы текущего terminal-completion profile         |
| Метрики новых profiles и расширение сравнения последствий | После [методики NL-108](METRICS.md) для текущего identity contract D16 |
| Deployment platform, sandbox и управление ключами         | M3, до соответствующего внешнего использования                         |
| Resolver и schema для SpecGraph bindings                  | После стабильного export contract, при отдельной реализации интеграции |

Исходный архив сохраняет историю проекта. При расхождении очередности работ используется актуальный roadmap; при расхождении утверждений о готовности — описание реализации и конкретные свидетельства проверки.
