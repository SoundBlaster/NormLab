# Парковочный PoC: расчёт и независимая проверка Lean

Дата: 22.10.2026. Задача: [#195](https://github.com/SoundBlaster/NormLab/issues/195).

## Что демонстрируем

**Фабула → ручная проверка → юридические обстоятельства → расчёт → Lean**.
Модель упрощённая, явно заданная для PoC. Юридическая экспертиза и нормативный
lock находятся за scope этой демонстрации и не блокируют проверку модели.

TypeScript производит результат. [Parking.lean](../lean/Parking.lean)
независимо определяет допустимость результата по девяти состояниям условий,
наличию пяти координат и названной сумме штрафа. Verifier **не вызывает
TypeScript evaluator для проверки его же ответа**.

Независимость здесь означает отдельное исполнение проверки, а не независимую
юридическую формализацию. Приоритет исходов задан декларативно (`AllowedOutcome`),
а списки причин и ветви — второй реализацией тех же задуманных правил.
Проверка обнаруживает расхождение реализаций; общую концептуальную ошибку,
одинаково перенесённую в TS и Lean (например, неверный scope условия), она
не обнаружит. Для PoC это осознанная граница гарантии.

Lean проверяет:

- точный статус с порядком приоритетов: конфликт → выход за scope → пробелы →
  опровергнутое условие → выполненные условия;
- точные списки конфликтов, ограничений, опровергнутых условий и пробелов;
- кандидат 5 000 ₽ только при `fragment-matched` и сравнение названной суммы;
- ровно две гипотетические ветви при одном неизвестном условии без пробелов
  координат; отсутствие необоснованных/потерянных ветвей в остальных случаях.

Также доказаны общие теоремы `conflict_blocks`, `unsupported_blocks`,
`matched_requires_complete`, `fine_only_when_matched`.

Человек устанавливает обстоятельства. Lean получает только их состояния,
наличие координат и числа. Свободный текст, цитаты, rationale и пользовательский
Lean-код в проверочную программу не подставляются. Проверка не превращает
предложение LLM в установленный факт.

## Подключение к приложению

Кнопка **«Рассчитать и проверить в Lean»** выполняет прежний draft-расчёт и затем
проверку конкретного результата. Пока операция идёт, кнопка показывает
«Расчёт и проверка Lean…». Новая immutable запись assessment v2 содержит
`result` и отдельный `verification`:

| Status проверки | Поведение                                                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `verified`      | Lean kernel принял конкретный результат; UI показывает «Lean проверил правила модели PoC».                                          |
| `rejected`      | Форма/привязка неподдержана либо Lean опроверг результат. UI показывает отказ, а draft и санкция скрыты в закрытом disclosure.      |
| `inconclusive`  | Lean отсутствует, истёк ресурсный предел или не подтверждён аудит аксиом. Draft-расчёт сохраняется, статус не превращается в успех. |

Verifier использует закреплённый Lean 4.30.0, отдельный приватный временный
каталог и предел 20 секунд на проверку. Аудит ожидает отчёты о case theorem и
всех четырёх общих теоремах; допустима только стандартная аксиома `propext`.
`sorryAx`, native-evaluation axioms, неожиданные отчёты и предупреждения
не дают `verified`.

Verification содержит digests входов, результата, неизменённого пакета,
формального профиля, statement и toolchain. Hash входов включает и пояснения
человека, хотя они не участвуют в логическом вычислении. Профиль фиксирует
соответствие condition IDs/kinds и санкции формальной модели; неизвестный пакет
не получает проверку по старым правилам.

Исходный `result.proof=none` сохранён как часть контракта producer и старой
истории. Фактическая проверка хранится в **`assessment.verification`**; её scope —
`parking-fragment-poc/v1`. Это не proof готовности действующего законодательства.
Manifest норм и его digest не изменяются.

Reader принимает старые assessments v1 без verification и новые v2, сверяет
пересчёт и bindings проверки. Новая запись не редактирует старую. После `await`
Lean сервер повторно проверяет ревизию текста и актуальный assessment head:
конкурентная правка даёт 409. Повтор одного request ID возвращает ту же запись.
Если в UI есть несохранённые правки, сохранённая проверка помечается как
относящаяся к прежним входам и теряет зелёное оформление.

При чтении история также сверяется с текущим `parkingProfileDigest`.
Проверка прежнего профиля сохраняется как историческое evidence, но получает
вычисляемую отметку `verifiedByPreviousProfile` и предупреждение «Проверено
прежней моделью PoC» вместо зелёного статуса. Исходный receipt не переписывается;
для текущего профиля нужен новый расчёт.

История предназначена для доверенного single-user PoC: записанный запуск Lean
не является подписанной внешним удостоверителем квитанцией. Старый сервер,
понимающий только assessment v1, не сможет прочитать новые v2; при откате нужна
совместимая версия reader или соответствующая копия данных.

## Фактический прогон пяти сюжетов

Планы: [walkthroughs](../fixtures/parking-pilot/walkthroughs/README.md).
Полные входы, результаты и metadata десяти проверок:

| Сюжет                     | Первый расчёт                                             | После уточнения                                            | Lean                    |
| ------------------------- | --------------------------------------------------------- | ---------------------------------------------------------- | ----------------------- |
| W01, забыл оплатить       | `fragment-matched`, 5 000 ₽; названные 3 000 ₽ отличаются | `fragment-refuted`, кандидат отсутствует                   | Обе проверки `verified` |
| W02, успешная оплата      | `fragment-refuted`                                        | `unsupported`: квитанция другого ТС                        | Обе проверки `verified` |
| W03, не помнит            | `incomplete`, несколько пробелов                          | `incomplete`, только оплата неизвестна; две условные ветви | Обе проверки `verified` |
| W04, сообщения расходятся | `conflict`                                                | `fragment-refuted` после решения человека                  | Обе проверки `verified` |
| W05, ошибка и исправление | `unsupported`                                             | `unsupported` после уточнения остальных границ             | Обе проверки `verified` |

**10/10** ответов соответствуют формальной модели для данных входов. Здесь
`verified` у `conflict`/`incomplete`/`unsupported` подтверждает корректную обработку
ограничения, а не наличие нарушения.

Прогон выполнен через реальный локальный HTTP API: создание черновика,
подтверждение контекста, сохранение и подтверждение ручного review seed,
человеческие findings, два расчёта и повтор идемпотентного запроса. История
сохранила обе записи. Seed содержит минимальное ручное утверждение с точной
цитатой, а не полный автоматический разбор фабулы. Дополнительные ответы человека
взяты из плана сценария. Это проверка механики PoC, **не benchmark extraction**;
платного inference не было.

Восемь семантически повреждённых кандидатов Lean отверг независимо от TS guard:
статус, сумма, список конфликтов, сравнение штрафа, список пробелов и потерянная
ветвь, неверный исход ветви и переставленные списки `unsupported`/`refuted`.
Отсутствующий Lean в отдельном процессе дал `inconclusive`. Отдельная регрессия
закрепляет текст диагностики ложной пропозиции в Lean 4.30.0: неизвестная ошибка
не получает `verified` и остаётся `inconclusive`.

Повторить без inference:

```sh
npm test
npm run test:lean
```

Парковочный integration файл можно запустить отдельно:

```sh
npx tsx --test tests/parking-lean.integration.ts
```

Локальные artifacts и tmp при этом направлять на разрешённый build/cache диск.
Для проверки production assets из отдельного build directory factory `createApp`
принимает `assetsDir`; обычный запуск по-прежнему использует `dist`.

Следующий ход — review/merge связки source pack → Lean PoC, затем обновление
демо, чтобы пользователь прошёл этот путь на своём тексте.
