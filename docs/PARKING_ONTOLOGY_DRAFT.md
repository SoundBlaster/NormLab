# Базовая онтология и обогащение кейсом

Дата: 2026-10-04. Статус: candidate design, не утверждённая семантическая модель; candidate package скомпилирован. Основание — [план](PARKING_PILOT_PLAN.md), [условия](PARKING_CONDITIONS.md), [corpus](../fixtures/parking-pilot/README.md) и уточнение автора: extraction должен опираться на базовую онтологию, обогащаемую нюансами кейса.

## Три разных слоя

| Слой                          | Что содержит                                                                                                                 | Кто может менять                                                         |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Базовая онтология             | Типы сущностей, отношений и значений: участник, роль, автомобиль, эпизод, время, источник, утверждение                       | Отдельный authoring/review процесс                                       |
| Предметное расширение parking | Размещение, парковочное место/зона, сессия, платёж, разрешение и понятия для определения scope                               | Отдельный review расширения; юридические правила принадлежат NormPackage |
| Case graph                    | Экземпляры сущностей, proposals о свойствах/связях, источники, review решения и неизвестные обстоятельства конкретной фабулы | AI предлагает; человек рассматривает; приложение сохраняет ревизии       |

Обогащение кейсом обычно означает новые экземпляры, свойства и утверждения на известном словаре. Новый тип или отношение — candidate ontology delta, а не автоматическое изменение общей онтологии. Версия словаря фиксируется внутри ревизии анализа; старые результаты не переинтерпретируются незаметно.

Это разделение не требует трёх отдельных сервисов в локальном пилоте. Достаточно разделить artifacts и ответственность в одном приложении.

## Минимальное ядро: candidate vocabulary

| Concept          | Значение                                                          | Ограничение                                                                                |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `Participant`    | Лицо, организация или иной участник с case-local identity и alias | Имя не является ID; разные роли не создают автоматически разных людей                      |
| `RoleAssignment` | Утверждение о роли участника в контексте эпизода/объекта          | «Водитель» и «собственник» могут совпадать, но не объединяются без основания               |
| `Vehicle`        | Автомобиль как объект с identity внутри кейса                     | Упоминание другого номера может относиться к другому автомобилю                            |
| `Episode`        | Ограниченный фрагмент события, выбранный для анализа              | Имеет предложения о времени, месте, участниках и автомобиле; границы тоже reviewable       |
| `TimeInterval`   | Начало/конец, timezone и точность                                 | Приблизительное время не нормализуется в точное; неизвестная граница сохраняется           |
| `Location`       | Предложенное место/адрес/зона                                     | Принадлежность Москве и правовой режим не следуют из названия автоматически                |
| `SourceDocument` | Исходная фабула или отдельный источник                            | Ревизия и digest задаются приложением                                                      |
| `SourceSpan`     | Фрагмент конкретной ревизии источника                             | Точная цитата/offsets; наличие цитаты подтверждает происхождение, не истинность            |
| `Assertion`      | Утверждение о свойстве, отношении или событии                     | Субъект, predicate, объект/значение, отрицание/неопределённость, attribution и source refs |
| `ReviewDecision` | Ручное решение о конкретном assertion                             | Отдельно от model output; не подтверждает юридический смысл словаря                        |
| `MoneyAmount`    | Сумма с валютой и точностью                                       | Сумма платежа и сумма санкции — разные контексты                                           |

`Assertion` позволяет представить положительное и отрицательное высказывание об одном predicate без разрушения графа. Нельзя записывать неподтверждённую связь как безусловный `owns` или `paidFor` рядом с review layer: само ребро должно иметь происхождение и review state.

## Минимальное расширение parking

| Concept / relation candidate                                    | Для чего нужен                                                                                   |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `ParkingPlacement`                                              | Размещение автомобиля на месте, с предложенным интервалом                                        |
| `ParkingPlace`, `ParkingZone`                                   | Различать конкретное место, зону и режим; не смешивать физический объект и нормативную категорию |
| `ParkingSession`                                                | Пользовательская сессия в системе оплаты; не равна физическому размещению                        |
| `PaymentAttempt`, `Payment`                                     | Отличать попытку, сообщение о списании и успешный платёж                                         |
| `PermitClaim`                                                   | Заявление о разрешении/льготе; достаточно для scope gate без полной модели льготы                |
| `SessionCorrectionClaim`                                        | Сообщение об исправлении; выявляет unsupported case без модели допустимости исправления          |
| `SanctionClaim`                                                 | Упомянутое наказание с привязкой к эпизоду и заявленной норме; не результат расчёта              |
| `placedAt`, `involvesVehicle`, `hasRole`                        | Связи эпизода, места, автомобиля и участников                                                    |
| `paymentTargetsVehicle`, `paymentTargetsZone`, `coversInterval` | Предложенная привязка платежа и покрытия                                                         |
| `supportedBy`, `attributedTo`, `aboutEpisode`                   | Происхождение и контекст assertion                                                               |

Список — candidate, без утверждения, что такие aliases уже существуют в Ontology registry. Точные domain/range, cardinality и representation выбираются до сборки compiler input.

`paid_regime` — утверждение о режиме, а обязательность оплаты/применимость льготы — вывод нормативного движка на проверенной модели. В онтологию не прятать правило «пять минут», размер штрафа или признание виновности.

## Как это работает на corpus

### P02: обычный платёж

1. Создать Participant, Vehicle, Episode, ParkingPlacement, ParkingSession и Payment proposals.
2. Предложить роль собственника, размещение и связи платежа с автомобилем/зоной, отдельно интервалы размещения и оплаты.
3. Привязать каждое assertion к цитате. Своевременность и покрытие вычислять приложением после review и нормативного lock.

### P04: неправильный автомобиль

1. Создать два Vehicle instances и исходный Payment proposal с привязкой к другому автомобилю.
2. Сохранить SessionCorrectionClaim и связь с сессией; после review вывести unsupported scope.
3. Не создавать новую версию онтологии: нюанс уже выражается базовыми экземплярами и отношениями.

### P09: конфликт

Сохранить два Assertions с противоположным содержанием об оплате одного эпизода. Не удалять одно ребро при поступлении другого. Противоречие выводится по совместимым subject/predicate/context; не любую пару разных высказываний объявлять конфликтом.

### Новый неизвестный нюанс

Сохранить raw mention и SourceSpan, отметить `unmapped`/candidate gap с описанием нужного понятия. Если оно влияет на исход, расчёт unsupported. Review фактов и review ontology delta — разные действия; подтверждение слов автора не добавляет новый доверенный тип.

## Роль JSON

JSON — сериализация предложенного case graph по фиксированной версии словаря. JSON Schema описывает допустимую форму, ограничения и ссылки; instance validation дополнительно проверяет resolution refs, цитаты, уникальность IDs и domain/range связей. Ни одна из этих проверок не удостоверяет факты и соответствие модели праву.

Планируемый envelope model output:

- `entities`: case-local instances с ontology concept refs и aliases;
- `episodes`: кандидаты эпизодов и связи с instances;
- `assertions`: положительные/отрицательные/неопределённые proposals с evidence и attribution;
- `unmappedMentions`: нюансы, которые не удалось выразить разрешённым словарём.

Review decisions, результат движка, receipt/proof status, normative/ontology locks и digest исходной фабулы принадлежат приложению. Модель не может сама присвоить им доверенный статус. Consumer JSON Schema и validator подготовлены в [extraction contract](PARKING_EXTRACTION_CONTRACT.md); runtime extraction ещё не подключён.

Обезличивание касается aliases и представления участника в UI. Цитаты из исходной фабулы могут содержать исходные имена: политика хранения и редактирования source spans требуется отдельно. Наличие aliases не делает сырой case graph полностью обезличенным.

## Использование проекта Ontology

Проверены локальные `SPECS/ontology/core-contracts.md` и `induction-protocol.md` в `~/Development/GitHub/0AL/Ontology`. Они разделяют candidate drafts, compiler evidence и approval; `ontologyc` компилирует inert YAML в normalized IR и TypeScript SDK.

Для NormLab предлагается подготовить candidate package, проверить через `ontologyc`, затем использовать сгенерированные registry/types/schemas как authoring artifacts. На каждый extraction запуск Swift compiler не требуется. Точный adapter к текущим generated schemas и instance validator ещё не проверен; готовая интеграция не заявляется. SpecGraph imports/locks — reference design из другого consumer, не автоматически готовый API NormLab.
