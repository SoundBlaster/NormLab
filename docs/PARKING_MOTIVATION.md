# Мотивы в парковочном пилоте

Задача: https://github.com/SoundBlaster/NormLab/issues/239.

Добавляем отдельный optional package `normlab.parking-motivation@0.1.0` и
исследовательский профиль `normlab.parking-motivation-proposal/v1`. Исходные
`normlab.case-core@0.1.0`, `normlab.parking@0.1.0`, действующие extraction v1/v2,
юридические обстоятельства, интерфейс и квитанции Lean не меняются.

Мотив — побуждающая причина действия или бездействия любого актора. Намерение
необязательно. Используем `Motive` и `MotivationHypothesis` из опубликованного
Ontology 0.1.1; собственные аналоги этих классов не вводим. Их статус upstream —
draft. Версии пакетов и хэши закреплены в отдельном artifact manifest.

## Первый проверяемый срез

Оператор предоставляет источник и контекст: доступные сущности, эпизоды,
действия/бездействия и источники речи. Модель предлагает мотивы **после этой
привязки**. Это позволяет отличить ошибку интерпретации мотива от ошибки выбора
актора или эпизода. Это ещё не измерение самостоятельного разбора всей фабулы.

| Профиль предложения               | Ontology / смысл                                                                       |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| Выбранное contribution            | `nlmot:ParkingContribution` → `contributionView` → `eventcore:InterpretationCandidate` |
| Содержание мотива                 | `motivcore:Motive.description`                                                         |
| Предложение мотивировки           | `motivcore:MotivationHypothesis`, выбранный view, action / omission                    |
| actorId или null                  | Связанная с выбранным view роль actor либо неустановленный актор                       |
| Цитата и speakerId                | Поддержка конкретного приписывания; говорящий не становится актором                    |
| positiveSupport / negativeSupport | Независимые основания «за» / «против», включая одновременное наличие                   |
| unreviewed                        | Предложение ожидает решения человека; это не истинность мотива                         |

Это документированный mapping, а не экспорт InstanceGraph: существующие
`eventcore-v1` и `eventcore-provenance-v1` не допускают узлы motivcore.
Сгенерированные схемы нового package проверяют форму объектов; межузловые
политики остаются manual. Бенчмарк отдельно проверяет допустимые ссылки и цитаты.

Наличие точной цитаты, её интерпретация и истинность описанного — разные проверки.
Модель не может выдавать trusted bindings, решения оператора, review authority,
физические snapshots, Delta, юридические findings или штраф. В этом extraction
профиле гипотеза требует хотя бы одной цитаты; неподкреплённая догадка остаётся
вопросом. Это ограничение потребителя, а не универсальное требование motivcore.

Отсутствие мотива в тексте не доказывает отсутствие мотива у актора. Отрицание
«не из экономии» поддерживает отрицательное приписывание, а не положительную
гипотезу «почему-то ещё». Цель «успеть» не становится состоявшимся последствием.
Мотив может соседствовать с обстоятельствами, существенными для нормы; этот
срез не принимает и не пересматривает такие юридические решения.

Бездействие владельца и скатывание машины имеют разные contribution/view.
Пустая собственная Delta бездействия не означает отсутствия последствий.
У рассказа без физических состояний обе Delta остаются неизвестными: экспортёр
их не создаёт. Причинная цепочка из рассказа также не становится доказанной.

## Набор и протокол

`fixtures/parking-pilot/motivation-v1/` содержит 24 авторские синтетические
русские фабулы. `inputs.json` хранит только источник и предоставленный контекст;
`reviewer-only.json` — ожидаемые anchors, scope, категории и семантические
контроли. Это development reference, без независимой разметки и без gold claim.

Проверяем явные, отсутствующие, неизвестные, отрицаемые, конфликтующие и несколько
мотивов; действия и бездействия; владельца/водителя/плательщика; несколько эпизодов;
«я» в письме; неизвестного актора; AI, машину, сообщество и природное явление.
Ожидания и хэши фиксируются до inference. Перестановка actor/episode и
превращение цели в факт включены как отрицательные семантические кандидаты.

Две роли модели проверяются отдельно:

1. Генеративная модель получает только источник, контекст и proposal schema.
   Offline scorer сравнивает **наборы точных опор и привязок с reference**,
   сохраняя пропуски, лишние предложения и ошибки протокола. Свободное описание
   мотива требует отдельной семантической проверки: одинаковые anchors не
   доказывают одинаковый смысл. Precision/recall здесь относятся только к
   reference signatures, не к юридической или общей case accuracy.
2. Категориальный verifier получает фабулу и одно конкретное приписывание мотива.
   Ответы compatible / incompatible / requires_review определены критериями.
   Планы совместимы с `evaluation/categorical_smoke.py`; их reference labels
   хранятся отдельно. Это отдельная задача, не рейтинг генераторов и verifier.

Запуск без сети:

```sh
npm run parking:motivation:check
npm run parking:motivation -- export /absolute/new/plan-directory
npm run parking:motivation -- score /absolute/plan-directory /absolute/responses.json
```

`export` создаёт новые файлы, не перезаписывая существующий каталог. Он не читает
ключи и не вызывает модели. `score` читает ответы в формате, описанном в README
набора; ответы связаны с requestId и неизменным планом. Для локальных команд
используйте TMPDIR и npm cache на проверенном TB5 согласно project instructions.

Статус live comparison: **не выполнялся**. Перед ним отдельно закрепляются точные
model/provider versions, requests/split, settings, лимиты calls/time/cost,
stopping rule и все outcomes. Созданный план не разрешает платный inference.
Подготовка и regression checks работают offline в пределах зафиксированной
авторизации в `EVALUATION_VERIFICATION_AUTHORIZATION.md`.
