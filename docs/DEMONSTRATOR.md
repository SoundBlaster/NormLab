# Первый содержательный демонстратор A/B/C

Статус: предлагаемый следующий срез, **ещё не реализован**. Основание — [замысел](VISION.md) и [переписка](DESIGN_NOTES.md). Задачи — M1 в [roadmap](../roadmap.md).

## Результат для пользователя

На одном синтетическом уголовно-правовом фрагменте посетитель видит исходную модель, её структурное упрощение и вариант реформы. Он меняет установленные обстоятельства, получает объяснение каждого изменения последствий и видит область проверенного утверждения.

Первый показ выполняется локально. Подготовка открытой публикации и размещение сервиса имеют отдельные этапы. Интерактивный сервис с недоверенными загрузками потребует изоляции и контроля доступа из M3.

## Состав эксперимента

| Артефакт       | Требование к следующему срезу                                                                       |
| -------------- | --------------------------------------------------------------------------------------------------- |
| Исходный текст | Собственный синтетический фрагмент с устойчивыми ID положений                                       |
| Модель A       | Формализация этого текста; source mappings и принятые трактовки                                     |
| Модель B       | Удаление повторов или вынесение общих условий при сохранении последствий                            |
| Модель C       | Явно описанное изменение общих правил; завершённые входы дают единственный полный результат в scope |
| Domain         | Конечный набор допустимых комбинаций значимых входов, с явными ограничениями                        |
| Queries        | Equivalence A/B и конкретные свойства изменения A/C с зафиксированным baseline                      |
| Evidence       | Результаты, ledger, проверенные counterexamples и связанные с запросом receipts                     |

Рекомендуемый минимальный объём — одно дело, один субъект, один эпизод и два-три взаимодействующих правила. Это ограничение объёма разработки, не утверждение о достаточности модели для реального уголовного права. Взаимодействия должны затрагивать как обязательное смягчение, так и явно заданное исключение или совместное применение.

Точный набор правил, ограничений domain и свойств C фиксируется в NL-107 до реализации. Произвольные численные санкции не становятся нормативными требованиями проекта из-за появления в примере.

Текущий fixture `120 → 80` и редакция `120 → 60` сохраняются как исходный сквозной пример. Они демонстрируют изменение одного множителя, но не содержат отдельную структурно упрощённую модель B и не подтверждают взаимодействие нескольких правил.

## Пользовательский сценарий

1. **Прочитать эксперимент.** Увидеть синтетический исходный текст, цель изменений B и C, список включённых правил и исключённые вопросы.
2. **Разобрать обстоятельства.** Отдельно увидеть narrative, мотивированные findings и открытые условия. Открытое основание смягчения сохраняет соответствующие ветви.
3. **Сопоставить последствия.** Получить A/B/C для одного snapshot; срок, штраф и дополнительные последствия отображаются отдельными компонентами.
4. **Открыть объяснение.** Для каждого изменения перейти к правилу, условию, источнику и шагу derivation; для неприменённой нормы увидеть основание в ledger.
5. **Исследовать поправку.** Изменить finding, создать новый snapshot и увидеть, какие результаты изменились. Старое вычисление остаётся доступным с исходными bindings.
6. **Проверить свойство.** Открыть equivalence A/B или ограничение для A/C; увидеть domain, assumptions, proof status и coverage.
7. **Разобрать counterexample.** Перейти к конкретному допустимому набору входов, нарушающему заявленное свойство, и повторить его проверку.

Объяснение должно строиться из структурированных данных результата. Для первого среза подходит детерминированный renderer; внешний AI не требуется.

## Контракт сравнения

У каждой проверки фиксируются:

- роли `baseline` и `candidate`, точные версии и semantic/provenance digests;
- domain и правила получения завершённых входов;
- mapping входов, квалификаций и типизированных последствий;
- заявленное отношение сравнения и assumptions;
- результат, certificate, statement и verifier/toolchain identity.

Если mapping не определён для части domain, эта часть отмечается как непокрытая. Область нельзя молча сузить после обнаружения неудобного примера. Смена domain или mapping создаёт новый query и новую проверку.

Для A/B базовое обязательство выглядит так:

```text
Для каждого завершённого x из объявленного D:
    Outcomes_A(x) = Outcomes_B(x)
```

Равенство относится к полным множествам допустимых структурированных результатов после зафиксированного mapping. Сравнение только выбранного interpreter результата недостаточно, если профиль допускает несколько решений.

Для детерминированного C:

```text
Для каждого завершённого x из объявленного D:
    существует ровно один y, такой что Permissible_C(x, y)
```

Для A/C каждое утверждение задаётся отдельно. Пример для двух детерминированных моделей с совпадающей схемой:

```text
Для x из категории S:
    prisonMonths_C(x) <= prisonMonths_A(x)
    fine_C(x) = fine_A(x)

Для x вне S, но внутри D:
    Outcomes_C(x) = Outcomes_A(x)
```

Это образец спецификации свойства, не уже принятое правило реформы. Если A задаёт диапазон, контракт должен назвать объект сравнения: допустимое множество, его границы или конкретное решение с provenance. Одна выбранная точка диапазона не представляет весь baseline.

## Обязательства проверки

| Обязательство               | Что нужно подтвердить                                                                         |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| Soundness                   | Каждый полученный результат допустим независимой семантикой модели                            |
| Outcome completeness        | Все допустимые результаты в заявленном scope представлены; ни одна условная ветвь не потеряна |
| Mandatory-rule completeness | Каждая обязательная норма в scope учтена либо имеет проверенное основание неприменения        |
| Determinism                 | Для завершённых входов C существует ровно один полный результат                               |
| Equivalence A/B             | Упрощение сохраняет последствия на всём объявленном domain                                    |
| Reform properties A/C       | Выполняется конкретное ограничение изменений либо предъявлен проверенный свидетель нарушения  |
| Binding integrity           | Подмена snapshot, версии, роли модели, domain или statement отклоняется                       |

Для конечного D допускается исчерпывающий обход. Полнота генерации D и проверка результатов входят в обязательства, если заявляется гарантия для всего D. Совпадение на выбранном corpus получает отдельный статус и не обозначается общим доказательством.

В planned receipt следует сохранять способ обоснования: проверка corpus, проверенный exhaustive finite domain или theorem для формализованной области. Точные имена полей входят в NL-101/NL-404; текущий API их ещё не обещает.

## Метрики демонстратора

До сравнения необходимо зафиксировать правила подсчёта:

| Метрика                                         | Назначение                                         |
| ----------------------------------------------- | -------------------------------------------------- |
| Положения, повторы, определения и отсылки       | Показать изменение структуры A/B/C                 |
| Условия, исключения и точки human judgment      | Показать сложность получения решения               |
| Изменённые категории и компоненты последствий   | Показать семантический эффект C                    |
| Покрытая область / заявленная область           | Показать пределы проверки                          |
| Успешное объяснение участником причины различия | Оценить понятность интерфейса в последующем пилоте |

Целевые численные пороги исследования устанавливаются после выбора fixture и методики. Сокращение текста не засчитывается как сохранение смысла; понятность требует наблюдения за пользователями.

## Критерии готовности M1

- [ ] Есть версии A/B/C с источниками, mappings, scope и описанием каждого намеренного изменения C.
- [ ] Один snapshot анализируется во всех трёх моделях через общий pipeline.
- [ ] A/B имеют проверенную equivalence для объявленного конечного D; для C проверено выбранное свойство и существование единственного результата на завершённых входах.
- [ ] Есть отдельный демонстрационный ошибочный вариант поправки: проверка находит и подтверждает counterexample к заявленному ограничению, сохраняя его как учебный artifact.
- [ ] Пропуск обязательного смягчения, потеря ветви, подмена роли baseline/candidate и повторный учёт запрещённого преобразования отклоняются.
- [ ] UI показывает составные последствия, полный ledger в scope, открытые условия и источник каждого изменения.
- [ ] Экспорт содержит сравниваемые bundles, query/domain/mapping, результаты и связанные receipts, достаточные для повторной проверки поддержанным инструментом.
- [ ] Отчёт перечисляет конкретные проверенные свойства, способ проверки и ограничения; текущий M0 сохранён как regression scenario.

Полноценный импорт внешних artifacts и установка replay-инструмента в чистой среде относятся к NL-503/NL-504. Второй несвязанный предметный домен — NL-105 — проверяет переносимость после этого демонстратора.
