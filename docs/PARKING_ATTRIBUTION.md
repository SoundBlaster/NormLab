# R4: привязка парковочного расчёта к сохранённой ревизии

Дата: 2026-10-25. Подготовка: [#227](https://github.com/SoundBlaster/NormLab/issues/227).
Runtime: [#229](https://github.com/SoundBlaster/NormLab/issues/229).
Основа: [контракт R3](ACTION_ATTRIBUTION.md). Код:
[ParkingAttribution.lean](../lean/ParkingAttribution.lean).

## Контракт результата

`NormLabParkingAttribution.Input registry` принимает зарегистрированное событие,
его Interpretation, humanAnchor, вид профиля, логические основания и каталог
правил. Сериализуемый scope вычисляется из этой записи и интерпретации.

`NormLabParkingAttribution.propose` возвращает исключительно
`Option (NormLabActionAttribution.GroundedTransition registry)`.
Доказаны эквивалентность успеха проверке профиля и сохранение точной записи/key
в принятом результате. Незарегистрированный scope нельзя передать вместо
RegisteredEvent; непривязанный результат имеет другой тип.

Этот вход теперь используется runtime-адаптером
[parking-binding.ts](../server/parking-binding.ts) и [ParkingRuntime.lean](../lean/ParkingRuntime.lean).
Существующий расчёт нормы остаётся независимой проверкой выбранных состояний.

## Явно непривязанный API

Схематические функции профиля R3 переименованы:

- `Profile.proposeUnbound`;
- `Profile.UnboundTransition`.

Неоднозначных compatibility aliases нет; attribution gate запрещает возвращать
прежние имена propose / GroundedTransition в namespace Profile. Этот слой проверяет переданные
логические основания без утверждения о наличии события в реестре. Его можно
использовать для исследований логики профиля; парковочный вход требует bound API.

`CheckParkingAttribution` проверяет прямые ссылки в типах и телах всех объявлений
парковочного namespace, включая private/generated. Обращения к этим двум
непривязанным API и их дочерним константам запрещены. Это проверка прямых ссылок
текущего модуля, не полный transitive policy checker: bound API внутри вправе
использовать низкоуровневый профиль.

## Конечный реестр

`EventRegistry.ofList(records, unique)` требует доказательства Nodup списка
`eventId` и автоматически получает key_matches. Для любой записи доказано:

```text
lookup(id) = some event ↔ event ∈ records ∧ event.key.eventId = id
```

Реестр не теряет исходные записи и не придумывает дополнительных. `ofList?`
проверяет уникальность вычислимо: успешность эквивалентна Nodup, а при дубликатах
возвращается none. Две записи с одним ID отклоняются даже при разных action,
интервалах или состояниях; молчаливой замены первой/последней записью нет.
Уникальность относится к одному снимку, как в R3.

## Проверяемый парковочный пример

В эпизоде 7 зарегистрированы размещение ТС (ID 101) и отсутствие оплаты (ID 102).
Водитель и собственник — разные Entity; водитель выбран actor/humanAnchor,
муниципалитет — target, ТС — instrument. Реестр собирается из конечного списка.

При явно заданных шести основаниях omission-профиля предложение принимается.
`accepted_record` и `accepted_scope` сохраняют выбранную запись, а
`driver_not_owner` фиксирует водителя, эпизод и ТС. Удаление явного основания
невыполнения даёт отказ (`unknown_rejected`); переиспользование ID размещения
для другой записи даёт отказ конструктора (`duplicate_ids_rejected`).

Пример проверяет контракт обработки входов. Он не устанавливает обязанность
водителя по действующему закону, истинность исходных свидетельств или санкцию.
Физические наблюдения и логические аннотации остаются разными состояниями.

## Runtime: что именно связывается

При расчёте ParkingLegal передаёт verifier неизменяемую копию исходной ReviewDraft.
Адаптер проверяет draft/revision, SHA-256 текста по действующему протоколу,
статус review, checklist, целостность цитат и ссылки на подтверждённые утверждения
того же эпизода. Для v2 дополнительно проверяются контекст и гипотезы; явный
read-only replay архивной reviewed v1 не выдумывает отсутствующие метаданные.

Пакет связывает полный канонический хэш ReviewDraft, состояния девяти findings,
ID источников и точные выбранные значения participant/vehicle/episode/date/location/
timeInterval. Строки кодируются без потерь по UTF-16 code units в ограниченные
hexadecimal Nat: пользовательский текст не становится кодом Lean. Это идентичность
выбранных координат, **не разрешение упоминаний в глобальный entity graph**.

Полная ревизия кодируется отдельным JSON encoder: ключи объектов сортируются,
порядок массивов сохраняется, допускаются конечные дробные значения, включая
confidence в originalExtraction. Значения вне persisted JSON отклоняются.
Ограниченный integer-only encoder нормативного IR остаётся прежним.

Node проверяет хэши/цитаты и готовит пакет; Lean не вычисляет SHA-256 исходного
текста. Kernel проверяет согласованность символического пакета: одинаковую ревизию,
уникальные ID источников, полный список условий и принадлежность каждой ссылки
подтверждённому утверждению выбранного эпизода (`supports_scoped`).

Это условная гарантия для **указанных** ссылок: finding может быть решением
оператора на основании сведений вне исходного текста. Binding v2 явно хранит
`uncitedConditions` для established/refuted/conflict без ссылок. Case-теорема
`uncited_checked` проверяет точное соответствие этого списка Request. Форма,
предложения и сохранённый результат показывают «решение оператора без ссылки
на источник». Наличие ссылки тоже не доказывает её релевантность или нужную
полярность; mapping «условие ↔ предикат/stance» вынесен в [#231](https://github.com/SoundBlaster/NormLab/issues/231).

RegisteredEvent описывает действие **оператора по фиксации разметки**. Его
before пуст, after содержит выбранный scope, состояния findings и ссылки.
Actor/humanAnchor — operator; target — выбранный participant; instrument — ТС.
Это логические снимки и шаг [0,1], не физическая длительность парковки.
Новый профиль не создаёт оснований required/capable/non-performance за водителя
и не выводит его ответственность. Unknown и conflict сохраняются как выбранные
состояния. Причинная истинность и юридическое установление не следуют из привязки.

ParkingAttribution.propose принимает этот зарегистрированный input. Доказаны
сохранение полного context и snapshot у принятого результата. Из того же Request
строится NormLabParking.Input: состояние каждого finding, присутствие координат
и claimedFine. Прежняя проверка результата, причин, суммы и ветвей не получает
отдельного несвязанного набора состояний.

## Квитанция, интерфейс и границы исполнения

`parking-fragment-poc/v2` требует binding для verified. В нём сохраняются scope,
sourceRevisionDigest, sourceStatementsDigest, findingsDigest и цитируемые UUID.
Новые binding имеют schema `normlab.parking-scope-binding/v2` и список uncitedConditions;
исторический binding v1 остаётся читаемым. History повторно читает архивную ревизию
и проверяет идентичность по сохранённой версии binding, без запуска текущих
reviewMetadataIssues, проверки цитат или finding admission-policy. Формат сохранённых
входов отделён от правил приёма новых решений; identity projections v1/v2 должны
оставаться неизменными, расширение требует новой версии. Изменение/потеря архива
по-прежнему даёт явную ошибку 409; это не механизм пропуска повреждённых квитанций.
Старые квитанции и прямой legacy verifier v1 остаются
читаемыми и не могут заявлять новое binding-поле. `Quot.sound` разрешён только
новому профилю вместе с propext; custom axioms и native-decide не допускаются.

UI в «Что именно проверено» показывает привязанный эпизод, участника, ТС,
ревизию и число ссылок. Формулировка — «сохранение выбранных идентификаторов»:
участник/ТС не сопоставляются с исходным текстом. Неподтверждённая проверка не подписывается как verified.

Verifier фиксирует исходники восьми локальных модулей и компилирует их по одному
в приватном request directory. Затем отдельный case импортирует полученные
артефакты. Это сохраняет по умолчанию лимит 512 MiB на Lean-процесс и общее окно 20 секунд
для компиляции/проверки; одно большое source-concatenation превышало память.
Одна parking-проверка исполняется за раз в процессе сервера; допускается один
ожидающий запрос. Ожидание не расходует 20-секундное окно исполнения, но входит
в durationMs; общий ответ ожидающего запроса поэтому может быть дольше 20 секунд.
Третий одновременный запрос получает явный inconclusive с сообщением о заполненной
очереди и возможностью повторить проверку вручную. Освобождение слота выполняется
в finally при успехе, отказе и сбое. Это локальная очередь одного Node-процесса,
не распределённый semaphore между репликами. Для staging с одним процессом
она предотвращает конкуренцию двух компиляций на одном CPU. Измерения reviewer
15,2 с на одном ядре и 35,8 с при двух одновременных расчётах не заменяются
нашими замерами на Mac; новых VPS-измерений этим PR не сделано.
Нет общего изменяемого кэша или зависимости от старых .olean. В finally удаляется
только созданный этим запросом каталог. Недоступность Lean, deadline и ошибки
компиляции сохраняют draft-расчёт с inconclusive, без утверждения о проверке.

## Replay сохранённого эпизода

Команда не вызывает модели и не изменяет source. Нужен новый output-каталог:

```sh
npm run parking:replay:bound -- \
  --source /path/to/saved-revision.json \
  --input /path/to/legal-input.json \
  --output /path/to/new-private-replay \
  --expected-outcome conflict
```

Output содержит приватную копию ревизии, новую квитанцию и redacted report.
[Evidence 2026-10-25](evidence/parking-bound-replay-2026-10-25.json): replay реальной
локальной сохранённой v1-ревизии с двумя противоположными подтверждёнными
утверждениями об оплате. Для технического replay выбраны source aliases narrator /
vehicle_1 / episode_1 и явное conflict в noPayment; остальные legal findings
остались unreviewed. Ожидаемый/фактический результат — conflict; две ссылки,
verified v2, успешное чтение новой квитанции и неизменный исходный файл.
Это проверка привязки и вычисления, не human-gold adjudication или качество extraction.
Исходный текст и координаты не включены в публичный report.

[Review follow-up replay](evidence/parking-runtime-review-check-2026-10-25.json)
фиксирует два последовательных verified при одновременной подаче, явный busy для
третьего запроса, один наблюдавшийся дочерний процесс Lean (sampling 20 ms), чтение
старой binding-v1 квитанции и новые квитанции с binding v2. Синтетический случай
из девяти established без цитат маркирует все девять условий как uncited;
это совместимость явного решения оператора, не подтверждение истинности условий.

[Fractional metadata evidence](evidence/parking-bound-fractional-replay-2026-10-25.json)
проверяет отдельно производную ручную копию той же ревизии с confidence 0.95,
p_yes 0.92 и вложенным confidence 0.875. Это синтетическая compatibility-проба,
не новый модельный ответ. Lean и чтение квитанции прошли; перестановка ключей
не меняет хэш, изменение confidence меняет его. Исходный архив не изменялся.

Команды в [RELATIONAL_FOUNDATIONS](RELATIONAL_FOUNDATIONS.md#воспроизведение) и CI
проверяют базовое ядро, парковочный вход и runtime-gate; последний проверяет
scope/snapshot/source identities и scoped references, axiom allowlist и отсутствие
прямого unbound API. Runtime gate теперь проверяет 275 объявлений. Отдельные runtime suites локально не запускались.

Следующий шаг — review и слияние runtime-моста, затем отдельная выкладка и
проверка того же сценария через веб. Подключение к production не следует из
локального replay и не выполнено этим изменением.
