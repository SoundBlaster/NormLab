# R4: подготовка привязанного парковочного входа

Дата: 2026-10-25. Ledger: [#227](https://github.com/SoundBlaster/NormLab/issues/227).
Основа: [контракт R3](ACTION_ATTRIBUTION.md). Код:
[ParkingAttribution.lean](../lean/ParkingAttribution.lean).

## Контракт результата

`NormLabParkingAttribution.Input registry` принимает зарегистрированное событие,
его Interpretation, humanAnchor, вид профиля, логические основания и каталог
правил. Сериализуемый scope вычисляется из этой записи и интерпретации.

`NormLabParkingAttribution.propose` возвращает исключительно
`Option (NormLabActionAttribution.GroundedTransition registry)`.
Доказаны эквивалентность успеха проверке профиля и сохранение точной записи/key
в принятом результате. Незарегистрированный scope нельзя передать вместо
RegisteredEvent; непривязанный результат имеет другой тип.

Это вход формального модуля, а не подключённый runtime-адаптер. Он ещё не
преобразует пользовательские findings или JSON в Lean-термы.

## Явно непривязанный API

Схематические функции профиля R3 переименованы:

- `Profile.proposeUnbound`;
- `Profile.UnboundTransition`.

Неоднозначных compatibility aliases нет; attribution gate запрещает возвращать
прежние имена propose / GroundedTransition в namespace Profile. Этот слой проверяет переданные
логические основания без утверждения о наличии события в реестре. Его можно
использовать для исследований логики профиля; парковочный вход требует bound API.

`CheckParkingAttribution` проверяет прямые ссылки в типах и телах всех объявлений
парковочного namespace, включая private/generated. Обращения к этим двум
непривязанным API и их дочерним константам запрещены. Это проверка прямых ссылок
текущего модуля, не полный transitive policy checker: bound API внутри вправе
использовать низкоуровневый профиль.

## Конечный реестр

`EventRegistry.ofList(records, unique)` требует доказательства Nodup списка
`eventId` и автоматически получает key_matches. Для любой записи доказано:

```text
lookup(id) = some event ↔ event ∈ records ∧ event.key.eventId = id
```

Реестр не теряет исходные записи и не придумывает дополнительных. `ofList?`
проверяет уникальность вычислимо: успешность эквивалентна Nodup, а при дубликатах
возвращается none. Две записи с одним ID отклоняются даже при разных action,
интервалах или состояниях; молчаливой замены первой/последней записью нет.
Уникальность относится к одному снимку, как в R3.

## Проверяемый парковочный пример

В эпизоде 7 зарегистрированы размещение ТС (ID 101) и отсутствие оплаты (ID 102).
Водитель и собственник — разные Entity; водитель выбран actor/humanAnchor,
муниципалитет — target, ТС — instrument. Реестр собирается из конечного списка.

При явно заданных шести основаниях omission-профиля предложение принимается.
`accepted_record` и `accepted_scope` сохраняют выбранную запись, а
`driver_not_owner` фиксирует водителя, эпизод и ТС. Удаление явного основания
невыполнения даёт отказ (`unknown_rejected`); переиспользование ID размещения
для другой записи даёт отказ конструктора (`duplicate_ids_rejected`).

Пример проверяет контракт обработки входов. Он не устанавливает обязанность
водителя по действующему закону, истинность исходных свидетельств или санкцию.
Физические наблюдения и логические аннотации остаются разными состояниями.

## Воспроизведение и следующий шаг

[Общие команды](RELATIONAL_FOUNDATIONS.md#воспроизведение) и CI компилируют шесть
модулей и запускают шесть gates с Lean 4.30.0, warningAsError и allowlist
`[propext, Quot.sound]` (R1: `[propext]`). Новый parking gate требует семь результатов
и дополнительно запрещает прямые ссылки на unbound API.

Следующий результат R4 — адаптер одного реального сохранённого эпизода: findings
и source IDs → конечные записи/интерпретации → этот bound entrypoint → проверенный
результат с сохранёнными участником, ТС и эпизодом. UI, деплой и inference в эту
подготовку не входят.
