# Hosted recovery UX: журнал, ошибки и следующие этапы

Дата: 2026-10-21. Ledger: [#179](https://github.com/SoundBlaster/NormLab/issues/179).
Исходные [sequence diagrams до / после](HOSTED_INFERENCE_RECOVERY.md) сохранены.

## Согласовано с пользователем

- Частичные фрагменты и классификации показываются сразу как непроверенные предложения.
- Начатая обработка продолжает выполняться на сервере после закрытия вкладки в пределах лимитов.
- После отказа API пользователь возобновляет работу по кнопке «Продолжить».
- Журнал действий и ошибок находится внутри каждого разбора и сохраняется на сервере.
- Новые ответы модели не перезаписывают более свежие ручные правки автоматически.
  Для прототипа достаточно явного конфликта и выбора применения; сложный merge engine не нужен.

Это продуктовая задача. Сравнения D1/Jev, новая библиотека и расширение evaluation
framework не являются её prerequisites.

## Первый реализованный срез: журнал и явные ошибки

UI parking review содержит панель «Журнал действий и ошибок» на shared design
tokens/components. `GET /api/parking/journal/:draftId` возвращает allowlisted
события и их количество. На экране последние 100 событий, новые сверху;
полные ревизии и записи запусков на диске не удаляются. Paging старого журнала
пока нет; UI сообщает об ограничении, если событий больше 100.

| Событие                      | Источник                                                           | Что показывает UI                                           |
| ---------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------- |
| Создан черновик              | Сохранённая первая ревизия                                         | Время и ревизию                                             |
| Ручные изменения / review    | История ревизий                                                    | Сохранение, число утверждений, подтверждённых и отклонённых |
| Применено предложение модели | Изменение originalExtraction между ревизиями                       | Требование проверки человеком                               |
| Начат авторазбор             | Приватный `extraction-<runId>/journal.json`                        | Отдельный ID запуска и исходную ревизию                     |
| Успех / сбой                 | Финальная запись запуска                                           | Время, длительность, результат или безопасную диагностику   |
| Конфликт ревизии             | Новая ревизия появилась до применения ответа                       | Правки сохранены, ответ модели не применён                  |
| Незавершённая запись         | Начало сохранено, финальная запись отсутствует и запуск не активен | Исход не подтверждён, автоматического повтора нет           |

Ручные действия проецируются из существующих ревизий: отдельной второй записи
для них нет. Журнал не копирует фабулу, цитаты, provider response bodies, значения
ключей или токены. Технические сведения раскрываются отдельно: ID запуска,
ревизия, длительность, количество утверждений; для ошибки — API family, этап,
код и доступный HTTP status. Модель, endpoint и usage не выдумываются: отдельный
контракт метаданных этапов ещё не подключён к этому UI.

HTTP 402 явно показывает требование оплаты; 429 остаётся лимитом/квотой без
предположения о точном состоянии баланса. Timeout/network/unavailable сопровождаются
предупреждением: запрос мог быть выполнен и оплачен. Invalid response не превращается
в semantic verdict. Сообщения provider exceptions и bodies не передаются в журнал.

Перед заменой уже сохранённых утверждений новым разбором нужна явная галка и
`replaceStatements: true` в POST `/api/parking/extract`. Сервер проверяет её до
нового provider call. Редактирование из другой вкладки вызывает conflict 409 по
expectedRevisionId, сохраняет более свежую ревизию и оставляет след в журнале.

### Границы надёжности первого среза

Начало запуска записывается до provider call; запись `journal.json` заменяется
через временный приватный файл и rename. Это защита от частично записанного JSON,
без обещания сохранности при физической потере диска или безусловного fsync.
Если не удалось записать завершение, начало остаётся и показывается как неизвестный
исход. Журнал не является транзакцией с ревизией и не выдаёт отсутствие финальной
записи за отсутствие выполнения/списания. Работа рассчитана на один процесс
владельца dataDir; multi-instance coordination не добавлена.

Исторические extraction folders без journal.json не получают выдуманных событий.
Активный запуск различается с незавершённой записью после перезапуска по текущему
процессу. Это наблюдаемость, **не crash-resume**. Ручная разметка остаётся доступна.

## Следующие срезы этой задачи

1. **Минимальный Job/Checkpoint contract.** Связать запуск с исходной ревизией,
   source digest, запросом/конфигурацией и caps. Состояния running, paused,
   completed и conflict; unknown хранить как outcome конкретной попытки.
2. **Частичные результаты.** Сохранять прошедшие проверку discovery и batches;
   выдавать отдельный unreviewed proposal и понятную незавершённость. Не пропускать
   обязательный этап и не выдавать частичное за полный результат.
3. **Возобновление по кнопке.** Проверять bindings, переиспользовать committed
   stages, сохранять unknown и прежние расходы. При ручных правках показать явный
   конфликт/применение, без автоматического merge. Поведение при закрытии вкладки
   и перезапуске сервера проверять отдельно.

Пока реализован только первый срез: **кнопка запуска начинает все этапы заново**.
Успешное discovery не переиспользуется, нет stage checkpoints, автоматического
retry/fallback, смены модели или новой фоновой очереди. UI сообщает это явно.
Закрытый evaluation framework не переоткрывается.

## Проверки

- Focused fake-provider regression: persisted failures/restart, unknown outcome,
  success с pending human review, revision conflict, явное разрешение замены,
  приватные поля, limit 100 без удаления истории и одинаковые timestamps.
- TypeScript, Oxlint и Steiger; полный локальный unit/API suite — отдельное evidence
  от GitHub CI и deployed service.
  Локально прошли **98 unit/API tests**, затем повторно **8 journal tests** после
  уточнения same-timestamp ordering; typecheck, lint/FSD и formatting успешны.
- Ограниченный browser walkthrough на синтетических HTTP 402/timeout: раскрыта
  диагностика, desktop viewport 1403 px / panel 1081 px, mobile viewport 390 px /
  panel 354 px, горизонтальное переполнение строк 0 на обоих размерах.
  Два свежих скриншота просмотрены; использовано 10 browser-вызовов. Reload
  persistence проверен API-тестом, не отдельным browser workflow. Console и полный
  accessibility audit не проверялись.
- Нет live inference, реальных provider credentials, dependency install или деплоя.

Следующий шаг: review первого среза, затем Job/Checkpoint contract и частичный
результат в той же Issue #179. Невыполненные acceptance остаются открытыми.

## Реализованное продолжение в исходниках

[Задания и checkpoints](HOSTED_CHECKPOINT_JOBS.md) добавляют app-owned background
работу, частичные pending proposals, explicit Continue, unknown acknowledgement и
revision conflict. Это не deployment evidence; см. отдельные ограничения и
verification в контракте. Исторические границы первого среза выше сохранены.
