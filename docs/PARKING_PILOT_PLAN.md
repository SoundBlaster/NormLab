# План локального прототипа: парковка в Москве

Дата: 2026-10-04. Статус: согласованный продуктовый план по интервью; реализация нового сценария ещё не начата. Документ фиксирует решения из текущей переписки и отделяет их от предложений, требующих проверки.

## 1. Цель и критерий успеха

Построить законченный локальный путь от свободного текста события до объяснимого вычисления состава нарушения и последствий для одного положения о московской платной парковке. Пользователь должен видеть, какие обстоятельства предложил AI, какие он сам подтвердил, чего не хватает и почему получен результат.

Первый пользователь — автор проекта: программист, увлекающийся правом, без профессиональной юридической подготовки. Он проверяет прототип в течение нескольких вечеров. Друг-юрист подключается, когда появится работающий сценарий и материал для предметной критики.

Долгосрочная цель — открытый для пользователей сервис с демонстрацией реальных норм. Публикация сервиса не означает публикацию исходного кода. Первый этап остаётся локальным и single-user.

Две гипотезы пилота:

- Подтверждение утверждений и явные пробелы позволяют человеку управлять переходом от фабулы к вычислению.
- Подготовка ограниченного нормативного пакета имеет измеримую стоимость; пилот помогает оценить трудоёмкость дальнейшей формализации.

Работоспособность модели и formal verification сами по себе не доказывают правильность юридической интерпретации, истинность фактов или жизнеспособность стартапа.

| Вопрос                  | Согласованное решение                                                                                      |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| Юрисдикция              | Россия, Москва                                                                                             |
| Сценарий                | Нарушения в зоне платной городской парковки                                                                |
| Первый нормативный срез | Часть 2 статьи 8.14 КоАП города Москвы; точный текст, зависимости и исключения проверяются до формализации |
| Субъекты                | Физические лица, личные автомобили                                                                         |
| Выход                   | Состав нарушения и последствия в поддержанном scope                                                        |
| Вход                    | Свободный текст; фото не поддерживаются                                                                    |
| Примеры                 | Синтетические фабулы; новости возможны как источник сценариев после проверки и обезличивания               |
| Нормы                   | Один зафиксированный проверенный пакет; без пользовательского выбора исторических редакций                 |
| Развёртывание           | Локальный прототип                                                                                         |

Процессуальное право, обжалование, сроки производства, эвакуация, юридические лица, все парковочные нарушения и весь КоАП не входят в первый срез. Упоминания таких обстоятельств не теряются: интерфейс явно сообщает, что система их пока не поддерживает и как это ограничивает ответ.

При необходимости используются зависимости из федерального КоАП, ПДД и правил парковки. Их включение определяется конкретными условиями выбранной нормы, а не стремлением заранее построить полную онтологию.

Отсутствие UI для версий норм не отменяет воспроизводимость: сохраняются текст источников, реквизиты, дата проверки и identity пакета. Размер санкции и условия оплаты в этом плане не фиксируются как проверенные юридические сведения.

## 3. Пользовательский путь

1. **Фабула.** Пользователь вводит описание. Черновик сохраняется между посещениями.
2. **AI-разбор.** Система предлагает участников, время, место, эпизоды и утверждения со ссылками на фрагменты исходного текста.
3. **Выбор эпизода.** Если событий несколько, пользователь выбирает один для обычного конвейера анализа. Остальные сохраняются в черновике.
4. **Подтверждение.** Пользователь вручную рассматривает каждое предложенное утверждение. Может подтвердить, отвергнуть, оставить открытым или добавить собственное.
5. **Уточнение.** Система показывает обязательные и опциональные обстоятельства, пробелы, противоречия и неподдержанные вопросы, объясняя их влияние на вычисление.
6. **Пересчёт.** По кнопке «Пересчитать» вычисляются применимость поддержанных норм, состав и последствия; результат связан с точной ревизией входов.
7. **Исследование.** Пользователь может посмотреть хотя бы один уровень условных ветвей и сравнить возможные результаты.
8. **История.** Предыдущие рассчитанные состояния доступны с исходными входами и основаниями.

Участники обезличиваются, даже если фабула содержит имена. Стабильные обозначения внутри разбора сохраняют роли и связи: например, «Водитель 1» и «Владелец 1» не должны автоматически становиться одним лицом. Время, место и участники представлены явно; неизвестные значения не выдумываются. Их обязательность для конкретного расчёта задаётся нормативной моделью, а не требованием заполнить весь процедурный документ.

## 4. Утверждения, пробелы и противоречия

- AI создаёт proposals, а не установленные факты. Каждое предложение сопровождается исходным фрагментом, либо явно отмечается отсутствие текстового основания.
- Подтверждение человеком означает выбранный вход модели, а не доказанную истинность реального события.
- Пользовательские дополнения отличаются от извлечённых утверждений и имеют своё происхождение.
- Отсутствие утверждения не означает отрицательный факт.
- Для обстоятельства «автомобиль находился в зоне платной парковки» нужен явный выбор «Да», «Нет» или «Не установлено». Обычная снятая галка не должна означать «Нет».
- Статусы review следует согласовать с существующей семантикой findings; UI должен различать «не рассмотрено», отрицание и недостаточность установления.
- Для вопроса показывается, зачем он нужен и может ли изменить исход. Обязательность относится к конкретной ветви вычисления.
- Противоречащие утверждения показываются рядом с источниками. Пользователь может выбрать одно, отвергнуть оба или сохранить противоречие открытым. AI не снимает его незаметно.
- Условия действия знака, нахождение автомобиля под его действием и применимые исключения рассматриваются отдельно, когда входят в поддержанный scope. Один статус человека, например инвалидность, не заменяет проверку всех условий.

Неизвестный факт, неподдержанная семантика и противоречие должны иметь разные объяснения. UI не выдаёт общий зелёный статус, скрывающий эти ограничения.

## 5. Условные ветви и упомянутая санкция

При недостатке существенных обстоятельств допускаются условные результаты. В первом прототипе достаточно одного наглядного уровня ветвления.

Выбор гипотетической ветви — исследование «что если», а не подтверждение факта. Чтобы перенести предположение в основной расчёт, требуется отдельное действие review.

Ветвление ограничивается обстоятельствами, влияющими на результат. Одинаковые результаты можно группировать с сохранением разных оснований. Конкретный лимит выбирается после оценки corpus. При его превышении система явно показывает неполноту исследования и предлагает уточнение; молчаливое усечение запрещено.

Если фабула содержит наказание или сумму штрафа, это отдельное исходное утверждение. Нормативный движок независимо вычисляет последствия и сравнивает их с упомянутыми:

- совпадает в поддержанном scope;
- отличается, с указанием расхождения;
- недостаточно данных или вопрос не поддержан.

AI-предложение санкции не показывается как проверенный результат до этого сравнения. Первоначальные слова автора фабулы сохраняются отдельно от вычисленного вывода.

## 6. Черновики, ревизии и актуальность

| Изменение                                        | Поведение                                                                                                                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Фабула или границы эпизодов после начала анализа | Предупредить о сбросе зависимой цепочки и запросить подтверждение; сохранить предыдущую ревизию и рассчитанное, начать новую; сбросить выбор эпизода и зависимые подтверждения |
| Одно обстоятельство                              | Сохранить подтверждения остальных обстоятельств; предыдущий результат отметить устаревшим до пересчёта                                                                         |
| Просмотр условной ветви                          | Сохранить основной набор установленных обстоятельств; не подменять его предположениями                                                                                         |
| Повторное открытие                               | Восстановить черновик и доступную историю                                                                                                                                      |

Сохранённые расчёты неизменяемы и связаны с точными входами и нормативным пакетом. Признак устаревания виден непосредственно у результатов, в том числе после прокрутки. Формальное подтверждение старого результата не переносится на новые входы.

## 7. Архитектурные границы

Планируемый конвейер:

```text
Фабула → AI proposals → schema validation → review человеком
       → выбранный эпизод и обстоятельства → нормативное вычисление
       → проверка результата в поддержанном scope → объяснение и история
```

- **AI adapter:** извлечение и предложения; строгий структурированный ответ, ограничение размера, timeout и явные ошибки.
- **Review layer:** происхождение утверждений, ручные решения, противоречия и ревизии.
- **Normative package:** проверенные источники, условия, исключения, последствия и границы поддержки.
- **Engine/checker:** вычисление на утверждённых входах и отдельная проверка в объявленном scope.
- **UI/storage:** законченный путь, черновики, immutable результаты и видимая актуальность.

Существующие contracts, snapshots, explanations и verifier используются там, где их семантика подходит. Наличие Lean proofs для synthetic A/B/C не означает доказанность нового парковочного профиля: его отношение и границы проверки нужно определить отдельно.

Проект `~/Development/GitHub/0AL/Ontology` рассмотрен как возможный инструмент описания сущностей, связей и генерации схем/TypeScript artifacts. Его schema validation не проверяет юридический смысл. Решение о зависимости принимается после минимального контракта: не расширять онтологию заранее и не требовать запуска Swift compiler на каждый пользовательский запрос.

Будущие пользователи смогут подключать доверенных агентов через Agent Surface Protocol. Сейчас ASP не реализуется; достаточно отделить AI adapter от предметной логики.

## 8. Локальный AI: проверенная отправная точка

На 2026-10-04 локально проверены:

- MacBook Pro, M4 Pro, 24 GB RAM.
- LM Studio API: `http://127.0.0.1:1234/v1`.
- Скачанная модель `openai/gpt-oss-20b`: около 12,11 GB на диске; загрузка показала около 11,28 GiB памяти.
- Загрузка с context length 4096 и parallel 1 успешна. Короткий запрос «Ответь одним словом: ГОТОВО» завершился ответом «ГОТОВО» примерно за 1,2 секунды.
- Ollama установлен, но его сервер во время проверки не работал. Найдены manifests Gemma3n e2b, Nomic Embed Text и Flux2 Klein; их inference не проверялся.

Начальный кандидат — LM Studio + GPT OSS 20B. Короткая проверка подтверждает доступность inference, но не качество извлечения, JSON compliance, latency длинной фабулы или юридическую компетентность. Доступность серверов и памяти меняется; перед разработкой интеграции её следует проверить повторно.

Для первых прогонов используются синтетические данные. Внешний AI provider не выбран. Политика хранения исходного текста и обезличивания требует явного описания перед вводом реальных персональных данных.

## 9. Этапы реализации и gates

Первый исследовательский срез: [реестр источников](PARKING_SOURCES.md) и [таблица условий с corpus seeds](PARKING_CONDITIONS.md). Документы содержат открытые зависимости и не означают закрытие нормативного gate.

Это план следующих работ, а не отчёт об их завершении. Сроки определяются после первого нормативного среза; обещание подготовить весь домен за несколько вечеров не даётся.

### Этап 1. Источники, scope и эталонные случаи

- [ ] Проверить точный текст выбранного положения и необходимых зависимостей по авторитетным источникам; сохранить реквизиты, текст и дату проверки.
- [ ] Выделить условия состава, исключения, последствия и существенные неизвестные обстоятельства.
- [ ] Составить таблицу поддержанных и неподдержанных случаев.
- [ ] Подготовить небольшой synthetic corpus с ожидаемыми фактами, пробелами, противоречиями и результатами.
- [ ] Зафиксировать спорные интерпретации отдельно, не превращать их в скрытые правила.

**Gate:** для каждого ожидаемого вывода есть прослеживаемые основания; неоднозначности и ограничения записаны. Ручная инженерная проверка не обозначается как заключение юриста.

### Этап 2. Контракт и оценка AI extraction

- [ ] Описать JSON-контракт эпизодов, обезличенных участников, ролей, времени/места, утверждений, source spans и упомянутых санкций.
- [ ] Определить validation и поведение при malformed JSON, пустом ответе, timeout и недоступном сервере.
- [ ] Проверить GPT OSS 20B на том же corpus, включая несколько эпизодов, отсутствующие данные, отрицания, противоречия и текст, пытающийся дать модели команды.
- [ ] Сохранить конфигурацию модели и prompts; измерить latency и объём ручных исправлений.
- [ ] При неудовлетворительном качестве сравнить доступный альтернативный локальный кандидат на одинаковых случаях.

**Gate:** предложения имеют корректную привязку к тексту; ошибки и придуманные факты выявляются измерением и review, а не скрываются успешной schema validation. Порог качества утверждается после baseline.

### Этап 3. Сквозной локальный прототип

- [ ] Добавить bounded нормативный профиль и определить подходящую независимую проверку.
- [ ] Реализовать ввод, draft persistence, extraction и выбор одного эпизода.
- [ ] Добавить индивидуальное подтверждение, ручные дополнения, уточнения и противоречия.
- [ ] Подключить пересчёт, объяснение состава/последствий и сверку упомянутой санкции.
- [ ] Показать условную ветвь без изменения установленных фактов.
- [ ] Реализовать сохранение ревизий, подтверждение сброса цепочки и заметную stale-индикацию.
- [ ] Предоставить воспроизводимую инструкцию локального запуска с AI runtime.

**Gate:** один поддержанный случай проходит весь путь; недостаточный и противоречивый ввод не получает необоснованный однозначный вывод. История не меняется задним числом.

### Этап 4. Проверка и пользовательский пилот

- [ ] Проверить положительные и отрицательные случаи corpus, ревизии, сброс подтверждений, stale results, ветви и ошибки AI runtime.
- [ ] Пройти UI самостоятельно; подтвердить desktop/mobile поведение и понятность ключевых действий.
- [ ] Дать автору несколько вечеров для работы с прототипом; записать затруднения и исправления.
- [ ] Подготовить работающие примеры и вопросы для друга-юриста; провести review, когда он подключится.
- [ ] По результатам решить, уточнять выбранный пункт или добавлять следующий нормативный фрагмент.

**Gate:** получены воспроизводимые свидетельства, список предметных замечаний и измерения стоимости формализации. Публичный запуск рассматривается отдельно после оценки данных, доступа и эксплуатации.

## 10. Метрики пилота

| Область            | Что измерять                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| AI extraction      | Пропущенные и придуманные утверждения; ошибки отрицания, ролей, эпизодов и source spans; доля некорректных структурированных ответов |
| Работа человека    | Число исправлений и уточнений; время от фабулы до проверяемого результата                                                            |
| Runtime            | Время extraction и пересчёта отдельно; timeout и ошибки локального сервера                                                           |
| Нормативная модель | Охват corpus; причины недостаточности/неподдержки; расхождения с ожидаемыми результатами                                             |
| Формализация       | Время поиска источников, моделирования, проверки и исправлений; число зависимостей и спорных интерпретаций                           |
| UX                 | Может ли пользователь объяснить вывод, увидеть ограничения и отличить гипотезу от подтверждённого входа                              |

Юридическая корректность, качество extraction и formal verification оцениваются отдельно. Целевые численные пороги определяются после baseline, до расширения scope.

## 11. Оставшиеся решения

Продуктовое интервью завершило основные границы. Следующие вопросы решаются на конкретных artifacts:

1. Точная нормативная модель и набор исключений после проверки источников.
2. Минимальный extraction contract и соответствие существующим findings/statuses.
3. Число случаев corpus, лимит ветвей и приемлемое время ответа после baseline.
4. Необходимость Ontology и объём повторного использования contracts/verifier.
5. Политика хранения исходной фабулы и степень обезличивания до работы с реальными данными.

**Ближайший ход:** подготовить источники и таблицу условий для выбранного нормативного среза, затем вывести из них corpus и extraction contract. Изменения кода начинаются отдельным следующим шагом после этого документа.
