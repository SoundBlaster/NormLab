# NormLab: ведение задач

Эти правила применяются к работе в этом репозитории. Инструкции вложенных
`AGENTS.md` дополняют их для соответствующих каталогов.

## Ledger и документы

- **GitHub Issues — canonical ledger задач.** Одна Issue описывает один
  самостоятельно проверяемый результат. Мелкие исправления внутри задачи не
  требуют отдельных Issues. Canonical ID — полный URL Issue: номера между
  репозиториями могут совпадать.
- Один GitHub Project объединяет связанные Issues NormLab, Platform и адаптеров.
  Project — представление ledger, а не второй независимый список задач.
- `roadmap.md` описывает этапы и ссылается на Issues; актуальный статус конкретной
  задачи хранится в ledger. Протоколы, решения и отчёты сохраняются в Git, а Issue
  содержит ссылки на их закреплённые версии.
- Сначала проверяй существующие Issues, включая закрытые и deferred, затем
  создавай новые. Не заводи дубли по сообщениям в чате или по каждому PR.
- Пока Project/Issues ещё не настроены, не выдумывай URL и не объявляй ledger
  созданным. Продолжай разрешённую работу; явно укажи, что синхронизация ledger
  ожидает отдельной настройки. Локальная заметка о такой работе — временный
  handoff, не новый canonical ledger.

## Минимальная запись задачи

Поля можно хранить в Issue body или существующих labels/Project fields. Не
создавай дополнительную таксономию labels и fields для каждой новой задачи.

| Поле           | Содержание                                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Result / scope | Конкретный результат и границы работы; основной репозиторий.                                                                |
| Type           | `implementation`, `experiment`, `research` или `operations`.                                                                |
| Priority       | `P0` — текущая блокировка/инцидент; `P1` — необходимо для ближайшего этапа; `P2` — плановая работа; `P3` — отложенная идея. |
| Status         | Один из статусов ниже, с причиной блокировки/откладывания при наличии.                                                      |
| Owner          | Текущий исполнитель; для агента — идентификатор текущей сессии/задачи, без выдуманного GitHub assignee.                     |
| Dependencies   | Полные Issue URLs, конкретные внешние условия или явно `none known`.                                                        |
| Acceptance     | Наблюдаемые критерии завершения, определённые до работы.                                                                    |
| Next action    | Один конкретный следующий шаг.                                                                                              |
| Evidence       | PR/commit, отчёт, версия dataset/protocol и реально выполненные проверки; до появления результата — `pending`.              |

Если Project Status настроен, используй его как единственное текущее поле
статуса. Иначе используй `Status` в Issue body. Не веди две вручную обновляемые
копии текущего статуса. Issue state должен быть согласован: `done`/`dropped`
закрыты; остальные статусы открыты.

## Статусы и зависимости

- `backlog` — задача записана, ещё не готова к выполнению.
- `ready` — scope/acceptance ясны, зависимости выполнены, разрешений достаточно.
- `in-progress` — исполнитель начал работу; owner и next action актуальны.
- `review` — конкретный результат доступен для review; указаны ссылки и pending checks.
- `blocked` — продолжение требует конкретного внешнего условия; записать его и
  действие, которое снимет блокировку. Истёкший лимит/нет доступа не равны успеху.
- `deferred` — сознательно отложено; сохранить причину и условие возвращения.
- `done` — acceptance выполнены, evidence приложены, обязательные проверки завершены.
- `dropped` — задача отменена/заменена; закрыть с причиной, не как выполненную.

Сначала завершай зависимости, затем запускай зависимые задачи. Если доступны
GitHub dependency relations, отражай их там; до настройки достаточно ссылок
в Issue body. Для нескольких независимо проверяемых результатов используй
parent/sub-issues. Одна задача может ссылаться на несколько PR в разных repos;
независимые результаты получают отдельные Issues. Правила соседнего repo сохраняются.

## Рабочий цикл агента

1. Прочитай актуальную Issue, зависимости, relevant roadmap/protocol и состояние
   Git/PR. Выбирай следующую `ready` задачу по приоритету в рамках поручения
   пользователя. Не возобновляй deferred работу автоматически.
2. Зафиксируй `in-progress`, owner и следующий шаг. По умолчанию в общем потоке
   NormLab держи 1–2 активные задачи; расширяй WIP при явном поручении параллельной
   работы. Не создавай сабагентов без соответствующего разрешения.
3. Обновляй ledger при существенном переходе: scope/зависимость изменились,
   возник blocker, опубликован PR/отчёт, завершился review. Не публикуй heartbeat
   comments с неизменным состоянием.
4. Перед `done` сопоставь каждый acceptance criterion с evidence. Если часть
   результата не готова, сохрани частичный результат и pending criteria; не
   закрывай задачу из-за завершения сессии или исчерпания бюджета.
5. В handoff/финале укажи Issue URL, сделанное, фактические проверки, остаток
   работы и один следующий ход. При недоступном GitHub честно сообщи, что запись
   ledger не обновлена; синхронизируй её после восстановления доступа.

Изменение Issue body сохраняет постановку и историю результатов: при существенном
пересмотре scope/acceptance оставь датированную запись с причиной. Закрытые Issues
не удаляй; при возврате работы объясни reopening или свяжи новую задачу.

## Evidence и границы разрешений

- **Merged PR завершает реализацию, но не автоматически деплой или эксперимент.**
  Связывай PR с Issue. Используй auto-close (`Fixes`/`Closes`) только если merge
  действительно выполняет все критерии задачи; иначе обычную ссылку.
- Различай local checks, GitHub CI, live provider calls и deployed verification.
  Не выдавай один вид evidence за другой. Pending/failing обязательные checks
  не позволяют объявлять соответствующий результат завершённым.
- Для experiments до inference фиксируй hypothesis, inputs/splits, protocol,
  metrics, stopping rule и разрешённые caps. Записывай все attempts, failures,
  unknown usage и ограничения выводов. Отрицательный результат завершает
  эксперимент, если protocol и acceptance выполнены.
- Candidate-label agreement не является human gold или полной case-level
  accuracy. Human adjudication, semantic review и completeness — отдельные
  критерии; валидный JSON/offsets их не заменяет.
- Priority и статус `ready` не разрешают платный inference, деплой, merge или
  расширение scope сами по себе. Используй действующую авторизацию пользователя.
  Не добавляй и не запускай tests без запроса пользователя; фиксируй реальный
  validation scope и ограничения. Не сохраняй ключи или credentials в ledger.

- [.agents/skills/normlab-task-intake/SKILL.md](.agents/skills/normlab-task-intake/SKILL.md)
  — найти/создать задачу, убрать дубли и декомпозировать результат.
- [.agents/skills/normlab-task-update/SKILL.md](.agents/skills/normlab-task-update/SKILL.md)
  — обновить статус/evidence, оформить handoff или проверить завершение.

Перед обращением к GitHub определяй текущий remote и Project из реальной
конфигурации, не из предполагаемых номеров/названий. Если `rtk` доступен в `PATH`,
выполняй shell-команды через `rtk` (`rtk proxy ...` для полного вывода).
Если `rtk` отсутствует, например в CI или контейнере, выполняй исходные команды
напрямую. Отсутствие `rtk` не блокирует Git/validation и не требует его установки.
